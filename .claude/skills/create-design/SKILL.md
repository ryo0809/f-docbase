# create-design

ヒアリングを通して要件定義書(Markdown)を作り、`docs/` に保存して、アプリで確認できるパスを報告する。

## 手順

必ず次の順で進める。選択式の質問は AskUserQuestion を使い、自由入力が必要なものは通常の質問で聞く。

### 1. モード選択

モードは `requirements`(要件定義書、テンプレート: `templates/requirements.md`)のみ。

- 選択肢が1つだけの質問は AskUserQuestion がエラーになるため、質問しない。「モードは requirements(要件定義書)で進めます」と伝えて次へ進む。
- 他のモードが追加された場合だけ、AskUserQuestion で選ばせる。

### 2. 保存先フォルダの選択

1. `docs/` 配下のフォルダを再帰的に列挙する(`docs/assets` は除く。空フォルダも含める)。ファイルの探索は Glob / Grep を使い、空フォルダの確認が必要なときだけ `ls` を使う。
2. AskUserQuestion で既存フォルダから選ばせる。候補は最大3件 + 「ルート(docs直下)」を示し、新規フォルダ名は「Other」で自由入力してもらう。候補が多い場合は直近に更新されたものを優先する。各候補の説明に、入っているドキュメント名を添える。
3. 新規フォルダなら、保存時に作成する。パスは `/` 区切りで、`..`、空要素、`assets` は使わない。

### 3. タイトル

通常の質問でタイトルを聞く(例: `ECパッケージ(開発要件整理)`)。

ファイル名はタイトルから決める。次の文字は半角スペースに置換し、連続する空白は1つにまとめ、前後の空白を除く。

`/ \ : * ? " < > | # %`

結果が空ならタイトルの入力をやり直してもらう。保存先は `docs/<フォルダ>/<ファイル名>.md`。

### 4. 既存ファイルの確認

保存先ファイルがすでにある場合は**更新前提**で進める。

- 次のどちらかに当てはまれば「既存あり」とみなす。
  - 保存先のファイル名と同名のファイルがある。
  - 選んだフォルダ内に、frontmatter の `title` が入力タイトルと同じ別名ファイルがある(タイトルから決めたファイル名と一致しないことがある)。この場合は、AskUserQuestion で「既存を更新(推奨)」か「新規作成」を選ばせる。更新を選んだら、そのファイルのパスを保存先にする。
- 既存ファイルを読み込み、frontmatter(タグ)と本文を把握する。
- ヒアリングでは、既存の記述を踏まえて「変更・追記したい点」を中心に聞く。すでに埋まっている節は、内容を示して変更の有無だけ確認する。
- 既存の内容は、ユーザーが変更を求めた箇所以外は残す。勝手に削除しない。

### 5. タグの確認

AskUserQuestion(multiSelect: true)でタグを選ばせる。選択肢は2件以上必要なので、候補が1件だけのときは「タグなし」を加える。

- 候補: 既存ドキュメントのタグ(`docs/**/*.md` の frontmatter `tags`、Grep で集める)のうち使用頻度の高いもの。更新の場合は現在のタグを先頭に出し、説明に「現在設定中」と書く。
- 新しいタグは「Other」で自由入力してもらう(カンマ区切りで複数可)。
- 選ばれなかった既存タグは外す。タグなしも可。

### 6. 要件のヒアリング

`templates/requirements.md` の節に沿って聞く。

- 1回に聞くのは2節まで(例: 1〜2節、3〜4節、5〜7節)。各質問には「たとえば〜」と例を添える。
- 質問は節の見出しごとに箇条書きにして、ユーザーが同じ構成で答えられるようにする。
- 一部の質問にしか答えがなかった場合は、答えのない質問だけを聞き直す。
- 回答が曖昧なら掘り下げる。ただし聞きすぎない。
- 更新の場合、既存の節に中身があるときは、その内容を示して変更の有無だけ確認する。

| 節 | 聞く内容 |
|---|---|
| 1. 背景・目的 | なぜ必要か、解決したい課題、達成したい状態 |
| 2. スコープ | 対象、対象外 |
| 3. 利用者・ステークホルダー | 誰が使うか、関係者、承認者 |
| 4. 機能要件 | 機能の一覧、概要、優先度(高/中/低)。ID は `F-01` から連番 |
| 5. 非機能要件 | 性能(同時アクセス数・表示速度)、セキュリティ(個人情報・認証・権限)、運用(可用性・バックアップ・監視) |
| 6. 制約・前提条件 | 期限、予算、技術的制約、前提 |
| 7. 未決事項 | まだ決まっていないこと、確認先 |

ユーザーが「わからない」「まだ決まっていない」と答えた項目は、推測で埋めず「7. 未決事項」に移す。

回答の扱い:

- 非機能要件は、箇条書きにせず表にする。列は `ID | 分類 | 項目 | 要件 | 備考` で、ID は `N-01` から採番する。分類は性能 / セキュリティ / 運用(必要なら可用性・保守性など)。1行には1つの要件だけ書き、複数の要件を含む回答は行を分ける。数値目標が未設定の項目は備考に書き、決めるべきものは「7. 未決事項」への参照を付ける。
- 機能要件は、回答を機能単位に分けて `F-01` から採番し、表にする。複数システムにまたがる場合は、先に「システム概要」の表(システム / 役割)を置く。優先度が答えられていなければ、前提(例: 同時開発)に基づく値を入れ、その旨を本文に書く。
- 略称や表記ゆれ(例: 「マカレル」→ Mackerel)は、解釈を報告に書く。
- ユーザーの回答にない内容を、事実として足さない。補足するのは論点の整理(未決事項の「決める内容」など)に限る。

### 7. 作成・保存

1. `templates/requirements.md` の構成(見出し番号)を保ったまま本文を作る。節の見出しは変えない。節の中は、読みやすさのために小見出しや表を足してよい。
   - 「4. 機能要件」「5. 非機能要件」は表にする(ID は F- / N- で採番)。
   - 表のセルに `|` を含めない。改行が必要なときは別の行に分ける。
   - 「7. 未決事項」は項目を並べただけにしない。分野(例: 技術・インフラ、設計方針、進め方)ごとに小見出しを付け、項目ごとに「現状」と「決める内容」を表にまとめる。項目間に依存や優先順があれば、小見出しの下に一文で書く。
2. frontmatter を付ける。

   ```yaml
   ---
   title: <タイトル>
   tags:
     - <タグ>
   updated: '<現在時刻のISO 8601(UTC)>'
   ---
   ```

   `updated` の時刻は `date -u +%Y-%m-%dT%H:%M:%S.000Z` で取得する。タグが無い場合は `tags` を省略してよい。
3. 保存先フォルダがなければ作成し、Write ツールで`docs/<フォルダ>/<ファイル名>.md` を書き込む。
4. `DOCS_DIR` 環境変数が設定されている場合は、`docs/` の代わりにそのディレクトリを使う。

### 8. 報告

レポートとして次を報告する。

- 新規作成か更新か
- 保存したファイルのパス(例: `docs/要件定義書/ECパッケージ.md`)
- タイトルとタグ
- **アプリで確認できるパス**: `http://localhost:3000/docs/<ドキュメントID>`
  - ドキュメントID は `docs/` からの相対パスで拡張子なし。各セグメントを URL エンコードする。
  - 例: `http://localhost:3000/docs/%E8%A6%81%E4%BB%B6%E5%AE%9A%E7%BE%A9%E6%9B%B8/EC%E3%83%91%E3%83%83%E3%82%B1%E3%83%BC%E3%82%B8`
  - 編集画面は `/edit/<ドキュメントID>`
- 作成した内容の要約(各節の要点)
- 「未決事項」に回した項目の一覧
- 開発サーバーが未起動の場合は `npm run dev` で起動するよう添える

## 注意

- 保存先は `docs/`(または `DOCS_DIR`)の中に限る。外へは書かない。
- ドキュメント以外のファイルは変更しない。コミットはユーザーが頼んだときだけ行う。
