# 要件定義書

## 1. 背景・目的

- 背景: ECパッケージ事業の開発経験をもとに、CMSを自作したい。ECパッケージでコンテンツを表示するための CMS である。
- 課題: ECサイトに必要なテーマ、コンポーネント、媒体コンテンツを一括で管理したい。
- 目的: 次の状態を実現する。
  - 運用担当者はコンテンツ管理に集中し、開発者はコード管理とテーマ、コンポーネントなどの開発・保守に集中する。
  - EC運用担当者と開発者で権限を分けてコンテンツを管理する。

## 2. スコープ

### 対象

- ECサイトに必要なテーマ、コンポーネント、媒体コンテンツの一括管理
- 初回の実装範囲: メインバナーを複数のUIで管理できるところまで
  - コンポーネント側では、UI・動作・データ埋め込み場所のみを管理する。
  - EC基盤側では、APIを連携させると、そのUIで表示・動作することを期待する。

### 対象外

- 明確な除外範囲は設けていない。EC関連の機能はほとんど扱う想定である(具体的な線引きは「7. 未決事項」を参照)。
- 連携できる外部サービスは現時点でない前提とする。

## 3. 利用者・ステークホルダー

### 利用者

| 利用者 | 権限・できること |
|---|---|
| 管理者 | すべての表示を確認できる |
| 開発者 | コード編集など、開発に必要な機能が表示された画面を閲覧できる |
| EC運用担当者 | 公開・非公開、コンポーネント選択、テーマ適用など、必要な確認と操作のみ行える |

### 関係者・承認者

- 後から検討する(「7. 未決事項」を参照)。

## 4. 機能要件

<!-- 優先度は「初回はメインバナーまでを実装する」を前提にした仮置き -->

優先度は、初回にメインバナー管理までを実装する前提で仮置きした値である。

### システム概要

| システム | 役割 |
|---|---|
| CMS管理画面 | 管理者・開発者・EC運用担当者が、テーマ・コンポーネント・メインバナーを管理する画面 |
| CMS API | 管理しているコンテンツ、コンポーネントの情報をEC基盤へ提供する |
| ECパッケージ(EC基盤) | CMS API と連携し、コンポーネントのUIでコンテンツを表示・動作させる |

### 機能一覧

| ID | 機能 | 概要 | 優先度 |
|---|---|---|---|
| F-01 | メインバナー管理 | 複数のUIから選択して、メインバナーの公開/非公開を切り替える | 高 |
| F-02 | コンポーネント管理 | コンポーネントのUI・動作・データ埋め込み場所を定義する | 高 |
| F-03 | EC基盤向けAPI提供 | EC基盤が、コンテンツとコンポーネントの情報を取得できるAPIを提供する | 高 |
| F-04 | 権限管理 | 管理者 / 開発者 / EC運用担当者の権限を、ログインユーザーごとに紐づける(ログイン画面を含む) | 中 |
| F-05 | テーマ管理 | テーマの登録と適用を行う | 中 |
| F-06 | コード編集画面 | 開発者向けに、コードを編集する画面を提供する | 低 |
| F-07 | AIによるコンポーネントコード生成 | 管理画面での設定をもとに、AIを使ってコンポーネントのコードを組み立てる | 高 |
| F-08 | コンポーネントのプレビュー | コンポーネントにAPIのレスポンスを埋め込み、管理画面でプレビューする | 高 |

## 5. 非機能要件

| ID | 分類 | 項目 | 要件 | 備考 |
|---|---|---|---|---|
| N-01 | 性能 | API応答 | すべてのAPIが200で応答し、レスポンスを返せること | 応答時間・同時アクセス数の数値目標は未設定(「7. 未決事項」を参照) |
| N-02 | セキュリティ | 機密情報の扱い | セキュアな情報を取り扱う場合は、マスクをかけるなどして保護する | 対象とするデータは未定(「7. 未決事項」を参照) |
| N-03 | セキュリティ | 認証 | ログイン画面を実装する | 認証方式は未定(「7. 未決事項」を参照) |
| N-04 | セキュリティ | 権限制御 | ログインユーザーごとに権限を紐づける | 権限の内容は「3. 利用者・ステークホルダー」を参照 |
| N-05 | 運用 | 監視 | SentryやMackerelでのアラート運用を検討する | 検討中(「7. 未決事項」を参照) |
| N-06 | 運用 | バックアップ | 後から検討する | 「7. 未決事項」を参照 |
| N-07 | 運用 | 可用性 | 未設定 | 稼働率などの目標は「7. 未決事項」を参照 |
| N-08 | セキュリティ | プレビューの隔離 | AIが生成したコードのプレビューは、管理画面本体から隔離した環境で実行する | 隔離の方式は未定(「7. 未決事項」を参照) |

## 6. 制約・前提条件

- 期限:
  - 初回リリース: 作成日(2026-10-05)の約1か月後
  - プロトタイプのサイト構築までにコンテンツをそろえる: 作成日の約3か月後
- 費用: 月額のランニングコストを数千円程度に抑える。
- 開発体制: 個人開発。自社運用を前提に開発する。
- 提供形態: 完成した製品を、企業に買い切りで販売する予定である。
- AI利用: コード生成にAIを使うため、AIの利用料が月額のランニングコストに加わる。
- 技術スタック: カスタマイズ性を優先し、Next.js で自作する(確定)。Next.js 以外の項目は提案中で、確定していない。
  - フレームワーク: Next.js(App Router) + TypeScript(確定)
  - UI: Tailwind CSS + shadcn/ui
  - DB: PostgreSQL(Neon または Supabase の無料〜低額枠)、ORM は Drizzle または Prisma
  - 認証・権限: Auth.js(メール+パスワード)と役割(admin / developer / operator)
  - 画像保存: Cloudflare R2 または Vercel Blob
  - ホスティング: Vercel
  - 監視: Sentry + Mackerel
  - API: Next.js Route Handlers(zod で検証、OpenAPI で契約を明文化)
  - モック: MSW または固定レスポンスの Route Handlers
  - テスト: Vitest + Playwright(主要導線のみ)
  - コード生成: Claude API などのLLM
  - プレビュー: Sandpack または sandbox 付き iframe
  - コード表示・編集: Monaco Editor
  - 既存ツールの利用: WordPress、microCMS、Payload CMS などの既存ツールはカスタマイズせず、自作する。
- 前提: 連携サービスはモックでレスポンスを定義する予定である。

## 7. 未決事項

### 進め方・体制

関係者・承認者が決まらないと、公開時の承認フローは決められない。

| 項目 | 現状 | 決める内容 |
|---|---|---|
| 関係者・承認者 | 後から検討する | プロダクトオーナーなどの関係者、公開時の承認者と承認フローの有無 |
| 対象外の範囲 | 明確な除外はなく、EC関連の機能はほとんど扱う想定 | 決済、在庫管理、受注管理、商品登録などを含めるか、含めないか |

### 技術・インフラ

技術スタックを先に決めると、認証方式とバックアップ方法の選択肢が絞れる。

| 項目 | 現状 | 決める内容 |
|---|---|---|
| 技術スタック | Next.js で自作することは確定。そのほかは「6. 制約・前提条件」の構成を提案中(未確定) | 提案どおりでよいか。特に DB・ORM・画像保存先の選択と、月額数千円に収まるかの見積もり |
| 認証方式 | ログイン画面を実装する予定。Auth.js のメール+パスワードを提案中 | 提案どおりか、外部認証も使うか |
| バックアップ | 後から検討する | 取得頻度、保存先、復旧手順 |
| 監視・アラート | SentryやMackerelで検討中 | 採用するサービス、通知先、アラート条件 |

### 品質目標

| 項目 | 現状 | 決める内容 |
|---|---|---|
| 性能の数値目標 | APIがすべて200で応答することのみ | 応答時間、同時アクセス数 |
| 可用性 | 未設定 | 稼働率の目標 |
| マスク対象のデータ | 「セキュアな情報はマスクする」のみ | マスクするデータの種類と、マスクの方法 |
| プレビューの隔離方式 | 生成コードを隔離して実行する方針のみ(N-08) | sandbox 付き iframe などの方式、ネットワークやストレージへのアクセス制限 |

### AIコード生成

| 項目 | 現状 | 決める内容 |
|---|---|---|
| 利用するAI | 未定(Claude API などを検討) | 利用するモデル、1回あたりの利用料の見込み、利用回数の上限 |
| AIのAPIキーの扱い | 未定 | 開発中は自社のキーを使う。買い手が自分のキーを設定する形にするか |
| 生成コードの承認 | 未定 | 生成後すぐ適用するか、確認・承認してから適用するか。バージョンの保存方法 |
| 設定からコードを組み立てる方法 | 管理画面の設定をもとに生成する想定 | 設定する項目(見た目の指示、APIレスポンスのサンプル、データ埋め込み場所など) |

### 製品化

| 項目 | 現状 | 決める内容 |
|---|---|---|
| 販売形態と納品物 | 企業への買い切りを予定 | 納品する範囲(ソースコード、ドキュメント、保守の有無)、買い手の環境への導入方法 |

### 機能範囲

| 項目 | 現状 | 決める内容 |
|---|---|---|
| ブロックエディタ | 要検討 | ページや本文を自由に組み立てるブロックエディタ(WordPress のようなブロックやコードブロック)が必要か。必要な場合は機能要件に追加し、エディタのライブラリを選ぶ |
